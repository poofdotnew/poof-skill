# Local Backend Guide

How to build and maintain a local PartyServer backend source tree that is later bundled and deployed to Poof. Use this when backend source is authored locally instead of edited by Poof AI.

This is the backend sibling to `docs/local-frontend-guide.md`: local source ownership, Poof-hosted policy/auth/database bindings, and Poof-managed deploy credentials.

## When to Use

Use this guide when:

- You are pairing a local frontend with a local PartyServer backend and deploying both artifacts to Poof.
- You need to add product API routes, webhooks, Heartbeat tasks, queue consumers, or Poof-native AI calls in local source.
- You have an existing local frontend-only project and need to add source-owned backend code without replacing the frontend.
- You already have a Poof project for policy/auth/database and want the Worker source to live in your own repository.

Do not use this guide when:

- Poof AI owns the backend source. Ask Poof AI to make backend changes with `poof iterate`.
- You only need a Poof-hosted backend generated by AI while you build a local frontend. Use `docs/backend-only.md`.
- You are trying to deploy raw TypeScript output. Use Wrangler's bundled Worker output.

## Source Ownership Model

| Mode | Source owner | Deploy/runtime owner |
|---|---|---|
| Source-owned local backend | You own the PartyServer source tree in your repository | Poof hosts the backend artifact, policy, auth, database, bindings, queues, and Heartbeats |
| Poof-owned backend | Poof AI owns backend source through `poof build` / `poof iterate` | Poof hosts everything |

For fresh local backend work, start from Poof's current PartyServer template and keep the standard template layout. Code download from Poof is a migration/sync tool for existing Poof-owned projects, not a prerequisite for a new source-owned backend.

For existing projects that already have a local frontend but no backend source, add the PartyServer template as a backend source tree and preserve the existing frontend. Do not reclassify the project back to Poof-owned source just to get backend code.

## Template Baseline

Start from the current Poof PartyServer template and keep the same conventions:

```text
partyserver/
|-- src/index.ts                  # platform middleware, Poof server init, route registration
|-- src/routes/index.ts           # product API routes and routeSpec[]
|-- src/lib/api-response.ts       # standard { success, data, error } responses
|-- src/lib/poof-auth.ts          # Poof auth validation for protected routes
|-- src/lib/poof-ai.ts            # Poof-native AI helper
|-- src/heartbeat/index.ts        # heartbeat registry and internal routes
|-- src/queues/index.ts           # queue registry and internal routes
|-- heartbeat.json                # recurring task declarations
|-- queues.json                   # queue declarations
|-- scripts/generate-api-spec.ts  # routeSpec -> generated API metadata
`-- wrangler.toml.template        # deploy-time Worker config template
```

Your repository can place this tree wherever its tooling expects it. The examples below use `partyserver/` as the backend root.

Keep platform plumbing in `src/index.ts`, `src/lib/*`, `src/heartbeat/index.ts`, and `src/queues/index.ts` unless a template upgrade or explicit platform change requires it. Product behavior belongs in route handler files, heartbeat task files, queue handler files, and small product-specific helpers.

## API Routes

Add product routes in `src/routes/index.ts` or files imported by it. For every route:

1. Register the route with `app.get`, `app.post`, `app.put`, `app.patch`, or `app.delete`.
2. Add the matching entry to `routeSpec[]`; `bun run build` generates the API spec from it.
3. Return the standard envelope with `sendSuccess` or `ApiErrors`.
4. Protect user-specific or write routes with `validatePoofAuth`.
5. Keep request bodies validated before mutation or external calls.

Example:

```typescript
import type { Hono } from 'hono';
import { ApiErrors, sendSuccess } from '../lib/api-response.js';
import { validatePoofAuth } from '../lib/poof-auth.js';

export const routeSpec = [
  { method: 'GET', path: '/health', description: 'Health check', auth: false },
  { method: 'POST', path: '/api/notes', description: 'Create a note', auth: true },
];

export function registerRoutes(app: Hono): void {
  app.get('/health', (c) => sendSuccess(c, { status: 'ok', timestamp: Date.now() }));

  app.post('/api/notes', async (c) => {
    const { walletAddress } = await validatePoofAuth(c);
    const body = await c.req.json().catch(() => null);
    if (!body || typeof body.title !== 'string') {
      return ApiErrors.badRequest(c, 'title is required');
    }
    return sendSuccess(c, { walletAddress, title: body.title });
  });
}
```

Do not bypass the template's CORS, request logging, x402, global error handler, heartbeat route registration, or queue route registration.

## Calling From the Local Frontend

The local UI should call backend routes through a shared API helper, not by hardcoding URLs in components. The backend URL comes from `poof project status -p <id> --json` connection info for the target environment.

Protected route calls must include the Poof auth token. Frontend helpers should handle token retrieval and unwrap the `{ success, data, error }` envelope before page components read fields.

## Poof-Native AI

For runtime LLM work, use the template helper:

```typescript
import { aiRun, aiRunForContext } from '../lib/poof-ai.js';
```

Do not add generic provider secrets such as `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, or OpenRouter keys for ordinary chat, classification, summarization, extraction, moderation, recommendations, scoring, or drafting. Poof supplies AI through its usage system. Only use a third-party AI credential when the user explicitly requires a non-Poof external provider and the reason is documented.

## Data, Auth, and Policies

Local backend source should still treat Poof policy/database/auth as canonical:

- The canonical project id and connection info come from `poof project status -p <id> --json`.
- The Worker is initialized through `@pooflabs/server` in `src/index.ts` and `src/lib/config.ts`.
- User authorization goes through `validatePoofAuth`; do not invent parallel JWT, cookie, or wallet-signature auth for product routes.
- Database schema and policy changes belong in the Poof project. After schema changes, sync any local frontend typed SDK if the UI uses one.

If a route depends on seeded rows, seed the Poof draft database through Poof build/iterate or the product's backend task. Do not hide missing backend state with in-source UI seed data.

## Heartbeats

Use Poof Heartbeats for recurring backend work. Do not create local cron services, background `setInterval` loops, GitHub Actions schedules, or side-channel daemon jobs.

Add tasks in `heartbeat.json` and task handlers under `src/heartbeat/`, then ensure `registerHeartbeatRoutes(app)` remains wired from `src/index.ts`.

Recommended scheduling pattern:

- Disable the top-level schedule for draft/preview unless the task truly needs to fire while developing.
- Enable the production schedule under `schedule.live`.
- Use the manual trigger path to seed draft or test a task.

See `docs/heartbeats.md` for the full task contract.

## Queues

Use Poof Cloud Queues for durable asynchronous backend jobs. Declare queues in `queues.json`, register handlers through `src/queues/index.ts`, and keep `/__internal/queues/:queueName` reserved for the platform dispatcher.

Do not create ad hoc polling loops or public "run queue" endpoints. Public routes enqueue work; queue handlers do the work.

## Build and Local Checks

From the PartyServer backend root:

```bash
bun install
bun run build
bun test
bun run dev
```

`bun run build` should typecheck and regenerate API metadata. Run it after routeSpec, heartbeat, queue, or route handler changes.

## Package and Deploy

Deploy local backend source as a built artifact. Use Wrangler's processed output, not raw `tsc` output:

```bash
cd partyserver
bun run build
rm -rf .poof-backend-bundle backend-worker.tar.gz
bunx wrangler deploy src/index.ts \
  --dry-run \
  --outdir .poof-backend-bundle \
  --name poof-local-backend-bundle \
  --compatibility-date 2025-08-15 \
  --compatibility-flag nodejs_compat \
  --compatibility-flag nodejs_compat_populate_process_env
mkdir -p .poof-backend-bundle/generated
cp generated/api-spec.json .poof-backend-bundle/generated/api-spec.json
cp queues.json heartbeat.json .poof-backend-bundle/
cat > .poof-backend-bundle/poof-backend-artifact.json <<'JSON'
{
  "entrypoint": "index.js",
  "wranglerVersion": "4.45.2",
  "apiSpecPath": "generated/api-spec.json",
  "queuesPath": "queues.json",
  "heartbeatPath": "heartbeat.json"
}
JSON
tar czf backend-worker.tar.gz -C .poof-backend-bundle .
poof deploy backend -p <project-id> --archive backend-worker.tar.gz --dry-run
poof deploy backend -p <project-id> --archive backend-worker.tar.gz
```

Keep the `cp` steps in sync with the manifest. Any path referenced by `apiSpecPath`, `queuesPath`, or `heartbeatPath` must exist inside `.poof-backend-bundle/` before the archive is created.

See `docs/backend-artifact-deploy.md` for the manifest contract and preservation semantics. Static UI deploys preserve the active backend artifact, and backend artifact deploys preserve the active static UI artifact.

## Verification

After backend changes, capture evidence for:

- `bun run build` in the PartyServer backend root.
- `bun test` when route/task logic has meaningful branches.
- Representative route probes against local dev or the deployed draft backend URL.
- `poof project status -p <id> --json` showing the canonical project and backend deploy state.
- `poof verify -p <id>` when lifecycle/policy verification is relevant and credits are available.
- Frontend browser preflight when the UI depends on changed backend behavior.

For deployed backend artifacts, smoke the draft backend URL from `connectionInfo.draft.backendUrl` and any frontend route that calls it. Do not call the backend "verified" only because the static UI built.

## Existing Local Frontend-Only Projects

When a project already has local frontend source but no backend source:

1. Preserve existing frontend files and product lifecycle tests.
2. Add a PartyServer backend tree from Poof's current template.
3. Add routes/tasks under that backend tree.
4. Update frontend API calls to read the draft backend URL from Poof connection info.
5. Run local UI and backend checks before deploying static/backend artifacts.

Do not download Poof backend source for this path unless the task is explicitly to migrate or reconcile an existing Poof-owned backend. Fresh local backend work starts from the template.

## Anti-Patterns

- Creating `backend/`, `server/`, `api/`, or `jobs/` beside the PartyServer backend root for product runtime logic.
- Editing platform middleware to work around a route bug.
- Adding generic LLM provider keys for ordinary AI work.
- Running local cron services for recurring work.
- Skipping `routeSpec[]` updates after adding routes.
- Returning custom response shapes from routes that the frontend then special-cases.
- Deploying raw `dist/` TypeScript output instead of Wrangler's bundled Worker output.
- Treating code download from Poof as required for new local backend work.
